# SAAS-CORE-API — Release candidate `1.0.0-rc.1`

**Statut :** candidate préparatoire — non publiée  
**Canal cible :** `rc`  
**Tag cible :** `v1.0.0-rc.1`  
**Dette :** D-017 — validation réelle dérivation + upgrade pilote

---

## 1. Objet

`1.0.0-rc.1` constitue la première base immuable destinée à l’exercice réel D-017.

Cette candidate n’est pas une release stable et ne doit pas être présentée comme `v1.0.0`.

Elle doit permettre de :

```text
figer une référence Core identifiable
→ dériver un dépôt pilote conservant l’historique Git
→ enregistrer la provenance dans core-origin.json
→ développer un petit module métier
→ produire ensuite une évolution Core compatible
→ valider un upgrade réel du pilote
```

---

## 2. Référence de départ

La préparation de la RC démarre depuis le `main` validé :

```text
commit : fe0c3821a7d2f9377066c98193df1e522131a0be
Core Gate #24
run : 35217570669
conclusion : success
```

Ce commit inclut la synchronisation documentaire post-D-016 et post-audit final.

La branche de préparation est :

```text
feature/d-017-derived-saas-upgrade-validation
```

Le SHA définitif de la RC ne sera enregistré qu’après validation, fusion et création du tag. Il ne doit pas être anticipé dans ce document.

---

## 3. Versioning attendu avant publication

La publication de la candidate exige l’alignement exact suivant :

```text
core-release.json
  version = 1.0.0-rc.1
  channel = rc

package.json
package-lock.json
frontend/package.json
frontend/package-lock.json
  version = 1.0.0-rc.1
```

Pour chaque lockfile, la version racine et `packages[""].version` doivent rester cohérentes.

Le validateur D-015 reste inchangé : aucune tolérance spéciale n’est ajoutée pour D-017.

---

## 4. Changements fonctionnels de cette candidate

La phase de préparation RC ne doit pas introduire de nouvelle fonctionnalité métier.

La candidate consolide le Core déjà validé avant D-017 :

- authentification et sessions ;
- compte utilisateur ;
- Workspace multi-tenant ;
- memberships, invitations, rôles et permissions ;
- Plans, Subscription, trial, entitlements et quotas ;
- Files sécurisés ;
- AuditLog ;
- administration Platform ;
- rétention/purge ;
- points d’extension métier ;
- centre d’aide sécurisé Workspace / Platform ;
- design system et préférences ;
- Playwright E2E Core intégré à la gate canonique ;
- gouvernance de release, provenance et migrations D-015.

Le module métier pilote `catalog` sera ajouté dans le dépôt dérivé, pas dans le Core.

---

## 5. Migrations

Aucune nouvelle migration n’est introduite uniquement pour préparer `1.0.0-rc.1`.

L’inventaire canonique reste :

```text
docs/releases/migration-manifest.json
```

Avant publication, `npm run release:verify` doit confirmer la cohérence entre le manifest, les scripts npm et les runners de migration.

Une application dérivée qui adopte cette RC doit examiner le manifest et exécuter uniquement les migrations réellement applicables à son état de données selon `MIGRATION-POLICY.md`.

---

## 6. Configuration

Aucune nouvelle variable d’environnement n’est ajoutée uniquement pour la préparation de la candidate.

Le produit pilote devra néanmoins revoir explicitement :

```text
.env.example
variables runtime
providers techniques
jobs
migrations
```

lors de la dérivation puis de l’upgrade, conformément à D-017.

---

## 7. Gate obligatoire

Avant toute publication :

```bash
npm run release:check
```

La gate doit valider notamment :

```text
release:verify
lint backend / tooling
tests backend
lint frontend
tests frontend
build frontend
Playwright E2E Core
```

La Pull Request de RC ne peut être fusionnée qu’avec le status check `Core Gate` vert.

Une nouvelle Core Gate sur le merge commit de `main` doit ensuite être vérifiée avant création du tag.

---

## 8. Publication cible

Lorsque toutes les validations précédentes sont vertes :

```text
tag : v1.0.0-rc.1
release GitHub : prerelease
commit : SHA exact du main validé
```

Le tag doit rester immuable.

La publication de la RC ne clôt pas D-017.

---

## 9. Provenance du futur pilote

Après création du tag, le dépôt pilote devra créer un `core-origin.json` avec le SHA réel publié :

```json
{
  "schemaVersion": 1,
  "repository": "greg44500/saas-core-api",
  "version": "1.0.0-rc.1",
  "tag": "v1.0.0-rc.1",
  "commit": "<SHA réel du tag>",
  "integratedAt": "<date ISO réelle>"
}
```

Aucun placeholder de ce document ne doit être copié comme une provenance réelle.

---

## 10. Limites connues

`1.0.0-rc.1` reste une release candidate de validation de distribution.

Elle ne signifie pas qu’un SaaS dérivé est automatiquement prêt pour la production. Les sujets dépendant du produit réel restent notamment :

- Billing / Payment ;
- conformité juridique/RGPD finale ;
- observabilité ;
- stockage Files de production ;
- sauvegarde/restauration ;
- déploiement, reverse proxy et infrastructure ;
- E2E métier du produit dérivé.

---

## 11. Condition de promotion stable

La promotion vers `1.0.0` stable reste interdite tant que D-017 n’a pas démontré :

```text
RC réellement dérivée
+ module métier pilote
+ provenance valide
+ évolution Core post-dérivation
+ upgrade réel du pilote
+ tests Core/métier/E2E verts
+ analyse des conflits
+ aucun blocker Core 1.0 restant
```
