# Core 1.0.0 — Release stable

**Version :** 1.0.0  
**Canal :** stable  
**Date :** 2026-09-17  
**Tag cible :** `v1.0.0`

## Objet

`1.0.0` est la première release stable du Core générique après validation du versionnement/provenance/migrations (D-015), des E2E Core Playwright (D-016) et de la dérivation + upgrade réels d’un SaaS pilote (D-017).

La publication stable ne signifie pas qu’un SaaS dérivé est automatiquement production-ready : les dettes propres au produit, à l’infrastructure, au billing, à la conformité et à l’observabilité restent à traiter lorsqu’elles sont applicables.

## Base validée avant préparation stable

```text
main : 5bf91252415e3e8f97b60c5aa1e165bd9829a3a2
Core Gate : #36
run : 35245765480
conclusion : success
```

Le tag `v1.0.0` doit pointer vers le commit `main` de la PR de release après validation de sa Core Gate post-merge. Le tag publié est immuable.

## Contenu fonctionnel

La stable reprend le périmètre fonctionnel validé du Core RC2, notamment :

- Auth, sessions et lifecycle Account ;
- Workspaces multi-tenant, memberships, invitations, RBAC et ownership ;
- Plans, Subscription, trial, entitlements, quotas et overrides ;
- Files sécurisés, corbeille/restauration/purge ;
- AuditLog et moteur générique de rétention ;
- administration Platform ;
- Design System et préférences validés ;
- centre d’aide Workspace / Platform sécurisé et extensible ;
- E2E Playwright des parcours Core critiques ;
- points d’extension métier et stratégie Git/provenance réellement éprouvés.

## Validation de la stratégie de dérivation

D-017 a exercé le dépôt `greg44500/saas-core-derived-pilot` avec le module métier `catalog` :

- dérivation depuis `v1.0.0-rc.1` ;
- évolution générique du Core ;
- publication de `v1.0.0-rc.2` ;
- merge réel de RC2 dans le pilote ;
- `MERGE_CONFLICT_COUNT=0` ;
- conservation des permissions, capability, migration, routes, RTK Query, navigation, dashboard et aide métier ;
- mise à jour de `core-origin.json` ;
- gates pilote #9, #10 et #11 vertes.

## Migrations

Aucune migration Core nouvelle n’est introduite par la promotion RC2 → stable. Les migrations Core existantes restent inventoriées dans `docs/releases/migration-manifest.json` et doivent être évaluées selon la provenance réelle du produit dérivé.

Les migrations métier d’un SaaS dérivé restent la responsabilité de ce produit ; la migration `catalog` du pilote n’est pas déplacée dans le Core.

## Configuration et dépendances

La promotion RC2 → stable n’ajoute :

- aucune variable d’environnement ;
- aucune dépendance ;
- aucun changement de contrat DB ;
- aucun changement applicatif métier.

Les changements de version concernent uniquement l’identité de release du Core et les métadonnées package/lock correspondantes, accompagnées de la synchronisation documentaire.

## Upgrade d’un SaaS dérivé

Un produit dérivé doit continuer à suivre la procédure contrôlée :

```text
git fetch upstream-core --tags
→ branche core-update/<version>
→ merge du tag Core
→ revue migrations / configuration / dépendances
→ tests Core + métier + E2E pertinents
→ mise à jour core-origin.json
→ Pull Request du produit
```

## Rollback / reprise

Un tag publié n’est jamais déplacé. Toute correction ultérieure doit produire une nouvelle version SemVer. En cas d’échec d’upgrade d’un produit dérivé, la branche d’upgrade est abandonnée ou corrigée avant intégration dans son `main`; le tag Core stable reste inchangé.

## Contrôles post-publication

Après publication de `v1.0.0` :

1. vérifier que le tag cible exactement le commit `main` validé post-merge ;
2. vérifier que la GitHub Release est non-prerelease ;
3. vérifier `core-release.json` = `1.0.0` / `stable` ;
4. conserver les tags RC1/RC2 immuables ;
5. utiliser `core-origin.json` pour tout futur dérivé ou upgrade.
